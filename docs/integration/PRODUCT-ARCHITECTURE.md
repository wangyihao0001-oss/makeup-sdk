# Design

> 业务接入参考：本文从 `dress/architecture.md` 迁移，描述 SDK 与业务服务、相机帧和私人资产的边界。产品仓库中的 `Agent.md` 等路径仍以 `dress` 为来源。

## Context

动机见 proposal.md。仓库里还没有小程序或服务端代码。试衣的运行约定已经写在 `Agent.md`：uni-app 微信小程序、一个 NestJS 业务服务、PostgreSQL、Redis 与 BullMQ、对象存储；换装走外部 API，密钥只在服务端，任务异步，图片按用途授权。`design-tryon-decision-mvp` 把供应商合同留到接入评估，不在这里重开。

试妆页面要求实时换色、按住看原图，实时帧默认不落库。

## Goals / Non-Goals

**Goals:**

- 试衣和试妆共用一个业务服务、同一套身份和私人资产授权，渲染路径分开。
- 妆效在手机上完成。保存的图就是拍下时导出的那一帧。
- 服务端能按所有权保存、列出和删除私人试妆，重复保存不产生第二条记录。
- 六类妆效的参数用稳定纹样 ID、色值、质感和 SDK 版本冻结。

**Non-Goals:**

- 本次不移植 SDK，不实现页面或接口。
- 不接入妆效供应商，也不用云端出图补设备不支持。
- 不开放脸型调整、模糊或自动选色。
- 不把试妆做成可公开帖，不改试衣任务的状态和幂等规则。
- 不定换装供应商合同、对象存储厂商和成图压缩参数。

## Decisions

### 1. 一个业务服务，只有试衣进异步队列

小程序只访问 NestJS。试衣的受理、查询、换装供应商回调和主动查询都进 BullMQ，由独立 Worker 调用 `TryOnAdapter`。试妆没有生成任务，不进这条队列，也不显示「等待处理 / 正在生成」。

曾考虑把试妆也做成异步生成任务。妆效既然在手机上已经画完，服务端再排一次队只会造出不存在的生成状态。

```
+------------------------ 微信小程序 (uni-app) ------------------------+
|                                                                      |
|  试衣: 人像 + 衣服              试妆镜                                |
|       |                          点击后才申请相机                     |
|       |                               |                              |
|       |                          OpenMakeup（移植后）                 |
|       |                          注入 camera / faceMesh               |
|       |                          apply / clear / getPatterns          |
|       |                               |                              |
|       |                          拍下: 导出当前帧 + 六类参数          |
|       |                          帧仍留在手机                         |
|       |                               |                              |
|       |                          仅「保存到我的试妆」才上传            |
+-------|-------------------------------|------------------------------+
        |                               |
        v                               v
+------------------------------ NestJS --------------------------------+
|                                                                       |
|  身份、资产授权、私人记录、亲友、广场                                   |
|                                                                       |
|  TryOnAdapter + BullMQ                 试妆记录接口                   |
|  换装供应商 API                        成图 + 参数                    |
|  密钥只在服务端                        不调用妆效模型                  |
|                                                                       |
|  PostgreSQL                           对象存储，按用途分开             |
+-----------------------------------------------------------------------+
```

### 2. 移植只替换输入和画布

产品调用的仍是 `apply(category, { color, pattern, finish })`、`clear`、`clearAll`、`getPatterns`。移植时用小程序相机帧实现可注入的 `camera`，把人脸结果交给可注入的 `faceMesh`，用小程序 WebGL canvas 替换 `HTMLCanvasElement`。着色器、纹样和清单格式保持 SDK 原有约定。

页面和 SDK 之间加一层产品门面。门面只暴露口红、睫毛、眼线、眼影、腮红、底妆。`morph` 和 `setBlur` 不从门面传出。色号一律用界面选中的十六进制颜色，不设置 `aiColor`。某个纹样加载失败时保留其他已画上的类别，和 SDK 现有行为一致。

初始化失败时停在设备不支持，并释放相机。不把实时画面改成上传。

### 3. 静态资源放在自有对象存储

FaceMesh 运行时、人脸模型、着色器和纹样不打进小程序主包。它们放在不含用户照片的公开静态前缀，进入试妆时按清单版本下载并在本地缓存。下载域名写入小程序合法域名。用户成图使用另一套私人前缀，访问仍走服务端授权后的临时地址。

### 4. 保存的是手机导出的成图

拍下时从当前画布导出图片，并冻结当时的妆容参数。这一步不上传。按住对比只在本地切换显示，不改参数，也不产生记录。

用户点击保存后，若尚未登录，先按现有按需登录完成，再上传。请求带客户端生成的保存请求 ID。服务端用所有者和该 ID 做唯一约束：重复提交返回同一条记录。上传失败时手机保留这次成图，允许用同一个请求 ID 重试。

继续调整在同一 SDK 版本和清单版本仍能下载时，恢复实时编辑。版本已不可用时，只展示已保存的成图和参数清单，不声称能重新叠出同一帧。查看历史记录不覆盖当前正在编辑的参数。

记录字段：

- 成图资产 ID、所有者、用途 `private_makeup_result`
- SDK 版本、清单版本
- 每一类的类别、色值、纹样稳定 `id`、质感
- 保存请求 ID、创建时间

不保存相机帧序列、人脸关键点或 `getPatterns` 的序号。

### 5. 私人试妆和试衣资产分开

两类图片都按所有者授权，都不能靠前端隐藏字段充当权限。用途分开存放，删除试衣素材时不连带走试妆成图，反过来也一样。试妆保存不创建亲友卡片或公开帖。以后若要分享，另建请求并复制用户明确选定的成图，不直接公开私人原图前缀。

试衣侧保持原链路：受理后返回任务 ID，同一提交不重复创建，主动重试才是新尝试，迟到回调不能改写已结束的尝试。成功结果不覆盖旧结果。

## Risks / Trade-offs

- [小程序相机帧或 WebGL canvas 喂不进现有渲染循环] → 移植限制在注入的 `camera`、`faceMesh` 和画布适配内。真机证明能跟上换色之前，不增加服务端妆效渲染。
- [首次进入试妆要下载模型和纹样] → 按清单版本缓存；主包保持轻量。下载失败时显示素材加载失败，已画上的其他类别保留。
- [清单更新后旧纹样 ID 对不上缩略图] → 记录带清单版本和稳定 ID。缺缩略图时仍显示已保存成图和色值。
- [端上内存或掉帧导致镜子不可用] → 归入设备不支持或追踪不可用，停止相机并释放资源。不改走上传出图。
- [成图已经导出到系统相册] → 删除私人记录只撤销服务端资产。相册副本按试妆设计的边界处理，服务端不承诺撤回。

## Migration Plan

当前没有生产数据，也没有旧的试妆记录需要迁移。实现顺序是：静态资源前缀和合法域名、私人成图上传与记录接口、真机移植验证、再把试妆镜接到这套接口。试衣队列可以并行做，不依赖 SDK 移植。

试妆入口用独立开关。关闭后停止新的保存，已保存记录仍按所有权可读。回滚应用版本时不恢复已删除记录的访问。试衣开关与试妆开关分开，避免关掉妆效时打断换装。

## Open Questions

- 成图用 JPEG 还是 PNG，以及压缩质量，实现时按体积和妆效边缘确定，不改变上传和记录结构。
- 对象存储选用哪一家兼容 S3 的服务，沿用 `Agent.md` 已留的选择，不改变授权方式。
- 换装供应商合同仍由试衣质量评估决定，不改变本设计里的适配器边界。
